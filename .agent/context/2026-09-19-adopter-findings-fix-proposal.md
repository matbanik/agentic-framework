# Adopter-findings fix proposal (Astra high, 2026-09-19)

## 0. Executive recommendation

Reserve `<project>/.agent/` for instructions, templates, context, and the existing project overlay; use `<project>/.agent-registry/` for a project-owned registry. Select that registry with `AGENT_MODEL_REGISTRY_HOME` in the current project session, preserving the existing explicit compiled-file override and shared-home support rather than adding an implicit directory search. The first shippable slice should join that layout decision to explicit registry deferral for sessions that will not resolve models or dispatch, a truthful preflight first-line result, and the corresponding adoption/profile instructions. Do not fill an adopter catalog with invented snapshots: use synthetic catalog data only inside isolated tests with dispatch disabled. Keep D6 adopter-supplied: record exact validation argv, working directory, scope, and success criteria in `PROJECT-PROFILE.md`, then register those commands during adoption instead of shipping an origin gate or interpolating executable text through a new token. Standardize all five artifact templates at `.agent/templates/`, repair copied links, seed `current-focus.md`, and make installer targeting and filename substitution explicit. Several findings need narrowing: escaped-pipe rejection already exists, agent renaming and Pomera substitution are already documented in the guide, and benchmark paths are confined to an opt-in mode. Live registry activation has an additional prerequisite: the packaged Python resolver/checker are forwarding wrappers, so a planner must identify an authorized source for their real implementations before promising a standalone first-install compile. Title the subsequent `/create-plan` **“Portable adopter bootstrap and first-plan contract repair”**, with the work packages and acceptance gates below.

This is a proposal, not an independent-review verdict or an implementation. Evidence was read in the requested order: the mock findings, the Source Project companion, both frozen probe documents, then the live package. Paths below are relative to `P:/agentic-framework` unless explicitly absolute; line numbers identify the inspected tree, not a future patched tree. Tests described below are proposed acceptance tests unless marked **observed**. No live model dispatch or implementation test suite was run.

## 1. Human decisions (must be in the plan, not guessed)

| id | decision | recommended default | why | what breaks if guessed wrong |
|---|---|---|---|---|
| HD-01 | Registry home versus instruction tree | Instructions at `.agent/`; new project-owned catalog at `.agent-registry/`; select it with a session-scoped `AGENT_MODEL_REGISTRY_HOME` | Separates independently owned content without inventing another implicit resolver rung | Copy/refresh can overwrite instructions, context, or catalog state; a global environment change can redirect unrelated projects |
| HD-02 | Empty-catalog adoption | Explicit no-dispatch deferral; synthetic catalogs belong only in isolated tests | Supports the probe's constraints without claiming a usable model binding | Fake ids reach a provider, or a deferred registry is mistaken for review readiness |
| HD-03 | Source of real registry compiler/checker | Name a reviewed working implementation and provenance before enabling live-registry adoption; retain the documented external prerequisite until a portable implementation is deliberately packaged | The live package contains forwarding wrappers, not these implementations | A fresh home forwards to itself or another forwarding copy and cannot compile; an uncontrolled import leaks another machine's pins |
| HD-04 | D6 integration | Documented adopter-supplied argv/procedure registration from the profile; no new `D6_GATE` token and no universal product gate | D6 already explicitly asks the human for domain-specific checks | A toy pytest command becomes a universal gate, or arbitrary command text is substituted into incompatible shells |
| HD-05 | Template source layout | `.agent/templates/{PLAN,TASK,HANDOFF,REVIEW,REFLECTION}-TEMPLATE.md`; artifact output locations remain governed by F1/F2 | Already matches the primary Step 2 destination and MANIFEST filenames | Workflows require extra copies with diverging content |
| HD-06 | Windows preflight interpreter and dispatcher support | Name the actual Git for Windows Bash executable for `.sh` preflight; retain PowerShell 5.1 support for the canonical `.ps1` dispatcher after encoding/parser gates pass | Avoids adding a second preflight implementation and honors the advertised shell contract | WSL checks a different environment, or preflight accepts a dispatcher that cannot parse |
| HD-07 | Workflow identifiers versus harness command registration | Document workflow ids and direct Markdown invocation; do not ship harness command adapters in this round | Fixes the promised interface without assuming untested harness wiring | A README slash label is treated as a registered command |
| HD-08 | Restricted review routing | C1/C2/C3b and E5 restrictions take precedence over automatic dispatch; route to B4's human reviewer and stop with the reason | Already required by the adoption guide's egress rule | Prohibited dispatch occurs, or a blocked review is treated as completed; `plan_to_exec_gate` is confused with permission to review |
| HD-09 | Research provider and D8 component mapping | Add explicit profile answers; retain the current manual substitution model and human-waiver requirement | The package already exposes these customization points but the interview is incomplete | Pomera is silently bypassed, or issue discovery assigns components from an unrelated repository layout |

**Steel-man of the rejected HD-01 option.** A shared instruction/registry `.agent/` can be safe and convenient if installation copies an exact file list into disjoint subpaths, checks collisions before writing, and preserves adopter-owned catalog and context files on every refresh. It retains the existing A10 wording, keeps the overlay beside the catalog, and avoids another top-level directory. This is a credible option for a carefully controlled installer. I reject it here because the live guide says to copy a directory, registry documentation and instruction documentation can share names, refresh ownership is already unclear, and there is no merge contract or protected-file inventory. Choosing it would require durable merge and refresh semantics; a sibling registry home resolves the observed collision with fewer assumptions.

These are recommendations for the human's next plan, not decisions silently enacted by this proposal. In particular, no existing `.agent/` registry should be moved or deleted automatically.

## 2. Per-finding fix specs

### 2.1 — Registry home collides with the instruction tree

- **Verdict + live citation:** **still-true**. `ADOPTION-GUIDE.md`, Steps 2 and 4, copy `core/.agent/` and then the package-root `.agent/` to a project `.agent/`. `ADOPTION-QUESTIONS.md:34` makes that A10's default. `.agent/INSTANTIATE.md:47-69` names the same workspace home but lists individual registry files. These instructions disagree about ownership and copy granularity. A particular copy command may merge rather than delete; the defect is the absence of a safe, specified operation, not proof that every copy primitive deletes the directory.
- **What:** A first install gives instructions and the live catalog distinct, unambiguous homes and preserves both across repeat installation.
- **How:** Adopt HD-01 in `ADOPTION-QUESTIONS.md`, `ADOPTION-GUIDE.md`, `.agent/INSTANTIATE.md`, `PROJECT-PROFILE-TEMPLATE.md`, `README.md`, `core/MANIFEST.md`, and `UPDATE-CHECKLIST.md`. Copy only the registry inventory in INSTANTIATE §2 into `.agent-registry/`; never copy package `.agent/context/`. Keep project overlays at `.agent/model-registry.local.yaml` and their existing compiled location. Set the selected home in the current process before invoking registry tools; document re-establishing it at session start. Do not persist a project path as a user-wide default. An intentional shared home remains an explicit environment configuration, not a second recommended first-install layout.
- **Tests:** Copy into an isolated adopter containing sentinel instruction/context files; verify their bytes remain unchanged when the registry inventory is installed. Assert that maintainer context does not appear in the adopter. Assert the selected home is `.agent-registry/` and the overlay remains under `.agent/`. Repeat the copy safely, and exercise a pre-existing conflicting destination so the recipe refuses instead of overwriting it. This would have caught F014 before the probe stopped.
- **Depends-on:** HD-01; land the layout, session setup, and 2.4 lookup documentation together. The copy mechanics share 2.14's recipe.
- **Suggested MEU/work-package name:** `adopter-registry-home-contract` / WP1.

- **How:** Prefer ASCII-only executable PowerShell sources for this package; replace non-ASCII comments/messages without changing behavior. Keep a temporary `pwsh` limitation in the guide only if the compatibility fix is delivered separately; remove it once the promised 5.1 gate passes.
- **Tests:** Byte gate: every shipped `.ps1` is ASCII or begins with the UTF-8 BOM. Instantiate representative names and paths, then parse with both PowerShell 5.1 and PowerShell 7 without execution. Test the post-instantiation artifact, because raw template tokens can themselves be invalid PowerShell. The wrapper's missing-prompt invocation should reach the usage diagnostic without launching a provider. A planted BOM-less non-ASCII message must fail the byte gate.
- **Depends-on:** Independent of registry installation; coordinate with 2.8 if substitution changes encoding behavior.
