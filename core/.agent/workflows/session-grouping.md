# Session MEU Grouping Workflow

Use this workflow when you have a body of work — **review findings, a new/under-planned build-plan phase, or a batch of recommendations** — and need to (A) express it as registered MEUs, then (B) bundle those MEUs into sequential build **sessions** sized to one-project-per-session, before any `/create-plan` run.

This replaces hand-writing a bespoke prompt each time. Invoke it as `/session-grouping <source>` where `<source>` is a build-plan phase id (e.g. `Phase 15b`), a path to a findings/review doc, or a short description of the recommendations to decompose.

This is a **PLANNING-phase-only** workflow. It produces draft artifacts (MEU registrations + a grouping proposal) and **hands off to `/create-plan`** — it is reversible, auto-proceeds like any draft, introduces **NO new HARD gate and NO turn-ender**, and sits strictly upstream of `/create-plan` §5 / GUARDRAILS SIGN 1. It never commits, reviews, or approves.

// turbo-all

## Two Stages

```
  <source>  ─►  STAGE A: findings → MEUs        ─►  STAGE B: MEUs → sessions      ─►  /create-plan (per session)
               (decompose, number, register)        (dependency graph + grouping)
```

- **Stage A** is SKIPPED when the source is a build-plan phase whose MEUs are already registered — go straight to Stage B.
- **Stage B** always runs; it is the core deliverable.

## Design Principles (shared with `/create-plan` Step 3 — cross-reference, do not restate)

1. **Dependency-first** — never group an MEU ahead of its prerequisites; foundation → roof.
2. **One project = one session** — each session is one continuous build pass; do not chain unrelated streams.
3. **Logical continuity** — shared files/context belong in the same session (maximize context reuse).
4. **Right-sized** — calibrate each session against the per-session token ceiling using **named past sessions**, not hardcoded constants (the Opus-4.8 tokenizer inflates ~20%).
5. **Single-plan-per-phase by default** — most phases map to one `/create-plan` run; multi-session fan-out is the **documented exception** the proposal must declare explicitly.

## Prerequisites

Read in order:

1. `AGENTS.md` §MEU Boundaries + §Planning Contract
2. `.agent/context/meu-status.yaml` (SSOT — never a stale rendered registry; see `.agent/skills/meu-status/SKILL.md`)
3. `.agent/context/triage-output.yaml` (**preferred source** when available — generated by `/issue-triage` workflow via `issue_triage.py triage`). Contains pre-classified issues, enrichment data, and proposed MEU batches.
4. **Fallback**: if `triage-output.yaml` does not exist, read `.agent/context/known-issues.yaml` directly (the SSOT) and the source named in `<source>`
5. The target `docs/build-plan/NN-*.md` phase spec, and/or the findings/review doc named in `<source>`
6. `docs/build-plan/build-priority-matrix.md`
7. One or two recent peers in `.agent/context/grouping/` for calibration (e.g. `p15b-*`, `p15c-*`)

## STAGE A — Findings → MEUs (skip if MEUs already registered)

**A1. Decompose.** From the findings/recommendations, derive a coherent MEU set: cluster related findings by shared file surface and dependency, severity-ordering the foundational ones first. Each MEU = one Manageable Execution Unit (one logical change with its own TDD cycle). Map each MEU back to the findings it covers (a traceability table).

**A2. Number + slug.** Assign the next free MEU numbers:
```
rtk rg -o "MEU-[0-9]+" .agent/context/meu-status.yaml --no-filename *> {{RECEIPTS_DIR}}/meu-max.txt
```
Take `max + 1`. Give each a kebab-case `slug`.

**A3. Build-plan home (if needed).** If the findings are not already covered by a `docs/build-plan/NN-*.md` section, author or extend one (e.g. a `NNx-*.md` remediation/feature doc) with source-labeled acceptance criteria per MEU (`Spec` / `Local Canon` / `Research-backed` / `Human-approved`). This is the canonical home the MEUs reference.

**A4. Register.** Add a phase entry (if new) and one `meus:` entry per MEU to `.agent/context/meu-status.yaml` (follow the existing entry schema: `row_key, id, slug, phase, band, matrix_item, build_ref, description, status: pending, status_labels, dependencies_raw, …`). Then regenerate the registry:
```
rtk uv run python tools/meu_status.py render *> {{RECEIPTS_DIR}}/meu-render.txt; Get-Content {{RECEIPTS_DIR}}/meu-render.txt | Select-Object -Last 5
rtk uv run python tools/meu_status.py render --check *> {{RECEIPTS_DIR}}/meu-check.txt; Get-Content {{RECEIPTS_DIR}}/meu-check.txt | Select-Object -Last 3
```
Confirm the drift check passes.

## STAGE B — MEUs → Sessions (always runs)

**B1. Dependency graph.** Using `sequential-thinking`, read the MEU set from the live SSOT (`tools/meu_status.py list --phase <id>` or the build-plan doc) and derive the dependency graph, the **critical path**, and any **parallel tiers** (MEUs with no mutual dependency).

**B2. Bundle into sessions.** Apply the Design Principles above. Group MEUs into sequential sessions: foundational/shared-file MEUs together, dependents downstream, GUI/docs after the engine they consume. Size each session against named past sessions (B-prereq read #5). Flag any session likely to exceed ~50% context as a split candidate.

**B3. Token calibration.** Estimate per-session in/out, each anchored to a **named** prior session of similar type — express as "calibrate vs {named session}", do not hardcode token constants.

**B4. Write the proposal.** Write to the canonical path (see §Naming) using the **required core** below. Optional sections may be added when the phase warrants.

### Grouping proposal — required core (+ optional)

| # | Section | Req? |
|---|---------|:----:|
| H | Header block: Source · Generated · Method · Origin · `Status: Active` · "reversible draft — not a gate" note | ✅ |
| 1 | **MEU / scope summary** — table: MEU · slug · covers (findings) · layer · depends-on | ✅ |
| 2 | **Dependency graph + critical path** — fenced graph + explicit critical-path line + parallel-tier notes | ✅ |
| 3 | **Recommended grouping — N sessions** — per session: MEUs, layer/files, why-grouped rationale, token est, split flag | ✅ |
| 4 | **Plan-creation pathway** — the `/create-plan` handoff: default single-plan-per-phase, or the ordered list of session slugs if fanning out | ✅ |
| 5 | Prerequisite gate (blocked-on / can-begin-now) | optional |
| 6 | Session summary roll-up table | optional |
| 7 | Token calibration sources | optional |
| 8 | Open decisions for the human (feeds `/create-plan` Step 2B) | optional |

> The required core is the union all prior proposals (p13–p15c, issue-triage) actually share. Do not invent sections an agent later can't fill.

## Handoff to `/create-plan`

The proposal is an **optional input** to `/create-plan` Step 3 "Reason About Project Scope":
- **Default (single-plan-per-phase):** the next `/create-plan <phase>` run reads the proposal and takes scope (MEU bundle + slug + build-plan sections) from it.
- **Multi-session fan-out (exception):** the proposal lists the session slugs in order; run `/create-plan` once per session block, in order. The proposal names which MEUs belong to each.
- If no proposal exists for a phase, `/create-plan` Step 3 falls back to its inline grouping (unchanged behavior).

This handoff never triggers a review, approval, or turn-ender.

## Naming (canonical)

```
.agent/context/grouping/{phase-id | YYYY-MM-DD}-{slug}-session-grouping.md
```
- **phase-id** prefix (`p15`, `p15b`, `p15c`) for build-plan phases; **date** prefix for non-phase batches (e.g. an issue-triage batch).
- Tail is always `-session-grouping.md`. Single canonical directory — no copies elsewhere.

## Exit Criteria

1. (If Stage A ran) MEUs registered in `meu-status.yaml`; `render --check` passes.
2. A grouping proposal exists at the canonical path with all required-core sections + a findings→MEU traceability table.
3. The Plan-Creation Pathway names the exact `/create-plan` invocation(s).
4. No code written, no review dispatched, no commit — this workflow is PLANNING prep only.

## Output

A session-grouping proposal (and, if Stage A ran, registered MEUs + an updated registry) ready for one or more `/create-plan` runs. Worked examples produced by this method: `p15b-help-search-session-grouping.md` (phase → sessions) and `p15c-risk-lens-correctness-session-grouping.md` (review findings → MEUs → sessions).
